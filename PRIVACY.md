# Privacy review — 2026-10-02, updated 2026-10-11 for version 2.0 (15), the release after 1.1 (7)

2.0 is the first release since 1.1 (public since 2026-10-07). It carries 1.2, 1.3 and 1.3.1 (never released separately), 1.4, 1.4.1 and the global work, including saved spots and the world catalogue (both reviewed 2026-10-11). The App Store privacy answer is unchanged: Data Not Collected.

## Implementation evidence

Nyx has no accounts, tracking, analytics/crash SDKs, advertising identifier, ATT prompt, CloudKit sync or server. No package dependencies. Journal notes/selected photos and saved parks live in SwiftData on-device; PhotosPicker is the only photo API. Location is requested in context, While Using only, and used for on-device distances. Choosing "Near me" is remembered across launches as a preference flag (`nearMe` in UserDefaults), never as a position; while location stays allowed, the next launch reads a fresh position without prompting, and with it no longer allowed Nyx falls back to the starting point and does not prompt. Local notifications contain rule-based forecast caveats. Field mode (2026-10-05) reads Core Motion's device attitude only while "Where to look" is open, to turn the sky to where the phone points; the phone's own attitude needs no permission prompt, is not recorded and never leaves the phone (true north is used only when location is already allowed). One part of field mode does prompt: "Where to look by sound" (build 8; off by default, switched on after an in-app explainer) reads head motion from AirPods or other headphones that report it (`CMHeadphoneMotionManager` in `SkyBeacon.swift`), and iOS asks once for Motion & Fitness access first, using `NSMotionUsageDescription` (`project.yml`). The head motion is used on the device while the compass is open, never stored, recorded or sent; if the person declines, the tone follows the phone instead. Its alarms are AlarmKit alarms on this iPhone, set only by the person after an in-app explainer; its Live Activity is started locally and updated by the app, with no push token or server. It changes screen brightness, auto-lock and night vision only while open and restores them on exit. Foundation Models receives small local source records and never calls a remote model.

`SafeHTTP` is the only network transport. It accepts HTTPS and exactly `developer.nps.gov`, `api.open-meteo.com` or `air-quality-api.open-meteo.com` (smoke/aerosol forecast, added with the owner's approval on 2026-10-05), rejects every redirect, uses one ephemeral session per service with cookies/cache disabled, and checks independent privacy preferences before each request. NPS alert requests always contain all 63 park codes (one request, at most every six hours); a ranger-program request contains the code of the park whose page is open; the campground request (one request, at most every seven days, held back on a Low Data Mode network, only after a park's "Where to stay" first appears) also contains all 63 park codes and nothing about the person. The NPS key travels in the `X-Api-Key` header: the bundled key, or a key the person entered in Your privacy → Advanced (kept in the Keychain on the device). Weather and air-quality requests for the parks always contain the public coordinates of all 63 parks (each park's first named viewing spot), together, in two requests of up to 50, never the device's location or a location-dependent subset. **Saved spots** (2.0; owner decision 2026-10-11) are the one exception, described below. **World catalogue places** (2.0; owner decision D3, 2026-10-11) are asked for by whole 10° tiles, also described below. With the one background mode (`fetch`, approved 2026-10-07), iOS may let Nyx repeat the same requests about every six hours, and only when a reminder, a Nyx widget, a followed night's Live Activity or the watch app uses the result: saved parks' forecasts, saved spots' forecasts (rounded as below) and followed catalogue places' regions, and park alerts; nothing else is sent, and with none of those in use a background run sends nothing. Network servers necessarily see an IP address and ordinary request metadata. Disabling updates prevents subsequent requests; an already transmitted request cannot be recalled.

**Saved spots** (2.0; approved by the owner on 2026-10-11). A saved spot is a place the person saves themselves: where they stand, typed coordinates or a pin. It is stored in SwiftData on the device (`SavedSpot`, with the exact coordinates, a name, a zone and region looked up on the device from the bundled places, and an optional note), and travels only in a journal export the person makes. For its live cloud forecast, `WeatherService.spotForecasts` sends api.open-meteo.com a request of its own, never combined with the parks': every saved spot's coordinates **rounded to 0.1°** (about 11 km; spots that round to the same point appear once), `hourly=cloud_cover` and the same forecast range and format as the parks' request, nothing else (no name, id, note or zone). The request therefore reveals roughly where the person's spots are, which Your privacy says in those words. It is made only while both "Cloud forecasts" and its own switch, "Clouds at your saved spots" (`spotForecastsEnabled`, on by default), are on, with the same transport, host guard, backoff, six-hour freshness and Background App Refresh cadence as the parks. The device's location is never sent unless the person saves it as a spot (and then only rounded). Saving where they stand reads the precise location once (`SaveSpotView`, best accuracy), keeps it in the spot on the device, and sends only the rounded position. Forecast detail (model comparison, cloud layers, cold, dew, wind) and the smoke forecast are never requested for spots. With the switch off or offline, a spot keeps its cached forecast and then uses its usual clouds from the bundled world grid. Spots reach the widgets, reminders and the watch through the same on-device paths as saved parks. This sends no new kind of data to the developer (there is no server); under Apple's definition the label stays Data Not Collected, as for any request whose content the service does not retain for the developer. Same three hosts; no new host.

**World catalogue places** (2.0; owner decision D3, 2026-10-11). Nyx bundles about 3,400 national parks and certified dark-sky places worldwide from Wikidata (`catalog.json`, the same file in every copy of Nyx). Their clouds are never asked for one place at a time. The world is divided into fixed squares of 10° of latitude by 10° of longitude; when a catalogue place is shown with its score (in Tonight's radius, on its page) or followed, `WeatherService.catalogForecasts` sends api.open-meteo.com one request for its square: the public coordinates of every catalogue place in that square, `hourly=cloud_cover` and the same forecast range and format as the parks' request, nothing else (no name, id or zone). Squares with fewer than eight catalogue places (remote islands, the far north) are asked about all together (about 330 places), so a lone island park is never named by a request of its own. A request carries at most 1,000 coordinates (a denser region is split by Wikidata number, not by position, so every part still spans the whole region), and one refresh asks for at most 2,000. A request therefore reveals a region about the size of a country that the person is interested in; it never says which place they look at, and it never carries where they are: only catalogue coordinates are sent, never the device's location. It uses the same switch ("Cloud forecasts"), transport, host guard, backoff, six-hour freshness and Background App Refresh cadence as the parks, and the forecasts are cached per place on the device. Forecast detail and the smoke forecast are not requested for catalogue places, and Nyx has no closure information for them (it points to the place's own website instead). A followed catalogue place reaches the widgets, reminders and the watch through the same on-device paths as a saved park, its record handed over whole (the watch still makes no request). Same three hosts; no new host; under Apple's definition the label stays Data Not Collected.

**Request pacing** (2026-10-11). Open-Meteo counts every place in a request as at least one call against its free limits (600 a minute, 5,000 an hour, 10,000 a day for each network address), so Nyx keeps its own pace: clouds are reused for six hours (an hour at the earliest when pulled to refresh), forecast detail for twelve (three when pulled; smoke never sooner than twelve), requests to one host go one after another, and a device never spends more than 400 calls in a UTC minute, 1,000 in an hour or 3,000 in a day on one host, of which browsing world catalogue squares may use at most 300, 700 and 2,000. A refusal (429 or 5xx) is waited out per host, honouring `Retry-After` or the limit Open-Meteo names, longer with each refusal in a row, kept in `nyx-backoff.json` across launches; nothing retries on its own. To do this, `CallLedger` keeps a list of the device's own Open-Meteo requests (time, host and the calls each counted as; no coordinates, no place, no identifier) in `nyx-calls.json` in Application Support, excluded from backup, for about two days. It is shown as today's count under Your privacy → Advanced and is never sent anywhere. Same three hosts; nothing new leaves the device. A background refresh makes no request at all when nothing outside the app shows a forecast (no reminders, no Nyx widget, no followed night, no watch app).

**Apple Watch** (added 2026-10-05): the watch app and its complications make no network requests; the network transport is not compiled into either watch target (`Scripts/verify_release.py` checks this). The iPhone hands the watch the saved park IDs, the starting park, the night-vision switch and the cached cloud forecasts through WatchConnectivity, which Apple carries directly between the paired devices (Bluetooth or local Wi-Fi), not through a Nyx server. Nothing goes from the watch to the iPhone. The watch keeps that context and its own choices (park, colours) in its App Group on the watch. No location, health or motion data is read on the watch.

`parks.json` contains NPS source URLs for provenance. They are not opened or downloaded by the app. Some links open in Safari, the system browser, only when the person taps them: a viewing spot's nps.gov accessibility page (URL from the bundled `accessible-spots.json`), Globe at Night (globeatnight.org, from a journal entry, nothing prefilled), the park's current-conditions page on www.nps.gov when NPS alerts are busy, a campground's reservation page from the NPS data (only on recreation.gov, www.recreation.gov, nps.gov or www.nps.gov; any other booking host is not linked) and the park's "Plan your visit" page on www.nps.gov (Where to stay, 2026-10-07), and (since 2026-10-07, for the licence credits in About the data) open-meteo.com and the Creative Commons BY 4.0 licence page on creativecommons.org. Nyx makes no request to any of them; they are SwiftUI `Link`s handed to the system, and `verify_release.py` checks the in-code list (`BrowserLink`: globeatnight.org, www.nps.gov, open-meteo.com, creativecommons.org; `StayLink`: www.nps.gov, www.recreation.gov; and `Campground.reservationHosts` for reservation links from NPS data). In 2.0, a catalogue place's Wikidata page (www.wikidata.org) and its official website (from Wikidata; linked only over HTTPS, so a site offered only over plain HTTP is not linked) also open in Safari when tapped; `verify_release.py` reads the allowed website hosts from `catalog.json` itself. Settings adds the privacy policy and support pages (get-nyx.com), the App Store review page (apps.apple.com, once the app has an ID) and the developer's email (mailto, handed to Mail); `SupportLink` joins the same check. The sky-glow and step-free data are bundled; nothing is downloaded for them. Research scripts/USNO fixtures are development tools, not runtime network code. Apple's location, Photos, Siri, model provisioning and device backup services are OS-managed; this review does not claim control over the operating system's network traffic.

**Delight (2026-10-06).** *Plan a trip* adds a night to Calendar through EventKitUI's `EKEventEditViewController`. Since iOS 17 that editor runs outside the app and needs no calendar permission: Nyx fills in a draft (title, park-local dark hours, the park's name as plain text, score notes, a `nyx://` link back to that night) and the person chooses the calendar and saves it, or cancels. Nyx never requests calendar access, never reads a calendar or event, and ships no calendar usage description. Trip plans, the journal's constellation, "skies you've seen" and the year recap are computed on the iPhone from bundled data, cached forecasts and park updates and the journal; nothing is fetched for them, and their share cards and plan text leave the phone only through the share sheet the person opens. The recap's optional wording uses the on-device model only and receives the recap's facts and up to a few short journal notes. *First light* uses location only when it was already allowed and only between 5 PM and 7 AM device time, once each time Nyx becomes active, to see whether the iPhone is at a park in true darkness; the position is used on the device and discarded, and a "first light shown" flag per park is kept in the app's preferences on this iPhone. Choosing an alternate app icon is a local system setting.

## Apple Vision Pro app (2026-10-05)

`NyxVision` compiles the astronomy engine, the score, the bundled tables, its own views and one network client: `CloudForecastClient`, whose allowlist on visionOS holds only `api.open-meteo.com` (the NPS and smoke hosts are not in the binary; `DataServices` and `ForecastDetail`'s fetching are not compiled in, which `verify_release.py` checks). It sends the same cloud request as the iPhone: the public coordinates of the 63 parks, nothing about the person (the service sees the headset's IP address, as any web request does). In 2.0 (work first built for 1.3.1, never released on its own) it also asks the same host, at most every twelve hours and behind the same switch, for the mid and high cloud layers at Haleakalā's summit viewing spot (`SummitLayerService`), so that park scores as on the iPhone; the request carries only that public coordinate. It is behind its own switch, "Cloud forecasts (Open-Meteo)" in Your privacy (on by default, enforced before any connection); the forecast is cached on the headset; the switch and the last chosen park are kept in UserDefaults (declared, reason CA92.1). With the switch off or offline, scores use each park's bundled usual clouds and are labelled that way. It requests no permissions (no location, photos, notifications or world sensing) and stores no journal or SwiftData. Its star names, constellation figures, volumetric Moon and visionOS widget (`NyxVisionWidgets`, its own empty manifest) are bundled data and add no network, permission or storage. Its manifest (`NyxVision/Resources/PrivacyInfo.xcprivacy`) declares tracking false, no collected data, and UserDefaults (CA92.1) as its only required-reason API. The privacy label stays "Data Not Collected".

## Platform surfaces (2026-10-06)

- **MetricKit, on device only.** Nyx subscribes to iOS's daily MetricKit reports (`MetricManager` on iOS 27, `MXMetricManager` on iOS 26) and keeps one number from them: the last average pixel luminance, with the date it covers, in the app's own UserDefaults. It is shown in About the data and Your privacy so people can see how dark Nyx keeps the screen. Nothing else from the report is read or stored, and nothing is sent: Nyx has no server or analytics. MetricKit is Apple's framework, not vendor code, and is not a required-reason API. Before a real report arrives the line is simply absent (DEBUG builds have a fixture labelled "Debug fixture, not a measurement").
- **Widgets, Spotlight, Siri and Shortcuts** compute from the bundled parks and the cached forecasts already on the phone. The medium widget's "next park" button stores the chosen park ID and night in the App Group defaults. Spotlight items for the 63 parks are public facts (name, state, Dark Sky designation), indexed into the device's own index.
- **Ask Nyx's tools** run the engine on the phone over the bundled parks and cached forecasts; the on-device model (Foundation Models' `SystemLanguageModel`) never uses Private Cloud Compute or any network service.
- **Reminders on iOS 27** carry the park's App Intents entity identifier (`appEntityIdentifiers`), so Siri can open the park from the notification. It is the park's public ID, local to the phone.
- **Followed nights (build 8).** "Follow this night" schedules the night's Live Activity on the phone with ActivityKit's iOS 26 scheduled start (no push type, no push token, no server). Its content is computed when it is followed: the park, its night's times, its score and its closure line. ActivityKit is the only record of which nights are followed. The tab bar's "night in progress" strip reads the same activities.
- **Handoff (build 8).** Park detail offers an `NSUserActivity` ("com.harrypakhale.nyx.park") carrying the park's public ID and the night's date, eligible for Handoff only (not for Spotlight or Siri predictions). The system carries it between the person's own devices on the same Apple Account; Nyx has no server. Its `appEntityIdentifier` lets Siri know which park is on screen.
- **Widget and control relevance (build 8).** The Tonight widget tells the Smart Stack the saved parks' dusk windows and a 25 km region around each saved park's first viewing spot (public coordinates from `parks.json`). The system matches the place on the device; Nyx asks for no location permission for this and is told nothing. The Tonight control and the Moon widget read the same App Group snapshot as the widget.
- **Journal by voice (build 8).** The journal schema intents (`.journal.createEntry`, `.journal.entry`) write to and read from the same on-device SwiftData store as the Journal tab. An entry's place is the park's own coordinates and name from the bundled library (a `PlaceDescriptor` built on the phone, no geocoding).

## Manifests

App, widget, watch app and watch widget each bundle `PrivacyInfo.xcprivacy`: tracking false; tracking domains empty; declared collected data empty; UserDefaults required reasons CA92.1 (own preferences) and 1C8F.1 (same developer's App Group preferences); the app alone also declares DiskSpace E174.1 (it checks free space before moving journal photos during the 1.1 to 2.0 store upgrade, and writes only when there is room). Allowed data hosts appear in a comment, not `NSPrivacyTrackingDomains`, because they are not tracking domains and Apple defines no general host-allowlist manifest key. No custom/unrecognized manifest keys were invented.

Direct source inspection found no file-timestamp, system-uptime or active-keyboard required-reason API usage. Ordinary file I/O and Date calculations are not those APIs. Build/Archive must include the manifests in both bundle roots. The development-signed archive validates locally with the correct App Group; this is not App Store distribution validation. Owner must generate Xcode's archive privacy report and validate the distribution export before uploading.

[Apple manifest documentation](https://developer.apple.com/documentation/bundleresources/adding-a-privacy-manifest-to-your-app-or-third-party-sdk) and [required API reasons](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitype).

## App Store privacy label — recommendation: Data Not Collected

Reviewed October 3, 2026 against Apple's [App Privacy Details](https://developer.apple.com/app-store/app-privacy-details/) definitions:

- Apple defines **collect** as transmitting data off the device so that *you and/or your third-party partners* can access it longer than needed to service the request in real time.
- Apple defines **third-party partners** as analytics tools, ad networks, third-party SDKs, or other external vendors *whose code you've added to your app*. Nyx embeds no vendor code; it calls two public web APIs with Apple's URLSession.
- Apple's own example: an IP address sent on a server call and not retained by you need not be disclosed.
- What leaves the device (2.0): public coordinates for all 63 parks, together in two requests of up to 50 (Open-Meteo forecasts and air quality, so they never reflect where the user is) and park codes (NPS). Saved spots: a separate cloud request with each saved spot's coordinates rounded to 0.1° (about 11 km), behind its own switch; it reveals roughly where the person's chosen places are, is not linked to any identifier, and reaches no developer server. The world catalogue: cloud requests for catalogue places, each with the public coordinates of every catalogue place in a 10° tile; they reveal a region about the size of a country, never the place looked at or the device's position. Alert and campground requests always name all 63 parks, so they reveal nothing about where the user is; a program request names only the park whose page is open. "From home tonight" (the Moon, darkness, planets and showers over the device location, a chosen city or the starting park) is computed on the device and requests nothing, so the person's coordinates still never leave it. Park updates can be switched off. A journal export (`.nyxjournal`) is a file the person saves or shares themselves; Nyx sends it nowhere. Crash and hang reports from MetricKit stay on the device and leave only if the person copies or shares them. The device's coordinates are never sent, unless the person saves where they stand as a spot; then only that spot's position, rounded to about 11 km, is sent for its cloud forecast. No journal, photo, identifier or account data is ever sent. The developer runs no server and receives nothing.
- [Open-Meteo](https://open-meteo.com/en/terms) states its logs are not linked to user identities, are not shared, and are deleted after 90 days. The NPS API is a public government service.

**Recommended App Store Connect answer: "No, we do not collect data from this app"** (shown on the store as Data Not Collected), with no tracking. This matches the spec (§3, §13). The privacy policy (`docs/privacy.html`) still tells users, plainly, that the three services (two of them Open-Meteo) see their IP address and links the providers' policies, so the label and the policy are consistent and nothing is hidden.

The publisher makes the final declaration in App Store Connect; this is the reasoning to rely on. Saved spots are the closest call: an ongoing request that carries a coarse position the person chose (or stood at), which Open-Meteo keeps in its logs for up to 90 days. Under Apple's literal definition it is not collected (the developer never receives it, and no Open-Meteo code is in the app), and the owner kept Data Not Collected on 2026-10-11 (DECISIONS.md G3). If App Review reads "third-party partners" more broadly, the fallback is Coarse Location → App Functionality → not linked to the user, no tracking; that changes the label and needs the owner's decision first. Revisit it if a vendor SDK, analytics, accounts, iCloud sync or a developer server is ever added.

## Age assurance (2026-10-07)

Texas SB 2420 (in force since 2026-06-04, per Apple) and later Utah and Louisiana laws ask apps to check the age range of accounts in those states. Nyx uses Apple's Declared Age Range framework (`Nyx/Services/AgeAssurance.swift`, entitlement `com.apple.developer.declared-age-range`):

- Once per launch, about 1.5 s after the first frame, Nyx asks iOS whether this account requires an age range (`isEligibleForAgeFeatures`, then `requiredRegulatoryFeatures` containing `.declaredAgeRangeRequired` on iOS 26.4+; `isEligibleForAgeFeatures` alone on iOS 26.2–26.3; nothing on iOS 26.0–26.1, where the system cannot say).
- Only when it does, Nyx calls `requestAgeRange(ageGates: 13, 16, 18, in:)`. iOS presents its own sheet or answers from its own cache.
- The response is discarded when the call returns: it is not stored (no UserDefaults, file, SwiftData or Keychain), not logged, not sent, and nothing in the app depends on it. Refusal and errors are silent. A per-process flag prevents a second request in the same launch; it is never written to disk.
- Under Apple's definition of "collect", nothing leaves the device, so the label stays Data Not Collected. Apple's framework, not vendor code, handles the exchange with the system. No required-reason API is involved.
- Not used: PermissionKit significant-change consent (nothing to consent to) and App Store Server Notifications (no server). Counsel review is still recommended (owner).

## Maps hand-off and translation

- **Directions in Maps** from a viewing spot (build 8): a user-initiated `maps://` link carrying the spot's public coordinates from `parks.json`, opened by the system in Apple Maps. Nyx makes no request and uses no MapKit; what Maps does is governed by Apple's policy. The product brief's "nothing else, including Apple routing services" refers to requests Nyx makes; this is a hand-off the person chooses. In 2.0 a saved spot's page offers the same Directions with the spot's own coordinates (unrounded, since only Apple Maps on the device receives them, at the person's tap; `SpotViews.swift`). `maps` is in `verify_release.py`'s scheme list.
- **On-device translation** of NPS alerts and ranger programs (build 8): when Nyx runs in a language other than English, a "Translate" button under "All park alerts" and under each ranger program opens Apple's Translation sheet (SwiftUI's `translationPresentation`), only when the person taps it. Translation runs through Apple's framework, on the device. On first use iOS may download Apple's language pack for that pair of languages; that is Apple's own system download, as for dictation, and Nyx neither makes it nor learns of it. Nyx sends nothing and stores nothing. No change to the label.

## Device verification still required

Use iPhone Settings → Privacy & Security → App Privacy Report. Exercise all screens with network updates enabled, then disabled; confirm app-initiated weather/NPS traffic matches the three hosts and no journal/device location appears in requests; with a saved spot, confirm its request carries one-decimal coordinates only and stops when "Clouds at your saved spots" is off. In the age-assurance sandbox (Settings → Developer), confirm the age-range sheet appears only for a regulated test account and that Nyx behaves identically after sharing, declining and an error. Check no permission prompt at onboarding, denied location retains manual planning, selected photo access only, local-notification removal after disabling, and no required-reason API omissions in the archive report. Device backups may include app data according to the user's OS settings; Nyx itself never uploads a journal.
